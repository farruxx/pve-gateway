# pve-gateway

[English](README.md) · **Русский** · [Oʻzbekcha](README.uz.md)

Небольшой веб-интерфейс, который превращает хост Proxmox VE в шлюз для его ВМ и контейнеров:

- **Порты:** проброс портов хоста на гостевые системы (iptables DNAT).
- **Домены:** маршрутизация `app.example.com` → `ip:port` гостевой системы через nginx, с автоматическими сертификатами Let's Encrypt и wildcard-сертификатами (`*.example.com`).

- **Без зависимостей.** Это один файл на Python 3, использующий только стандартную библиотеку и управляющий `iptables`. И то и другое уже есть в Proxmox VE 7 и 8.
- **Вход с учётной записью Proxmox.** Учётные данные проверяются через локальный API PVE; по умолчанию разрешён только `root@pam`. Вместо этого можно перейти на локальный пароль.
- **HTTPS сразу после установки.** Используется сертификат Proxmox (`/etc/pve/local/pveproxy-ssl.*` или `pve-ssl.*`).
- **Безопасно рядом с другими правилами.** Всё находится в собственных цепочках (`PVEGW_PRE`, `PVEGW_POST`, `PVEGW_FWD`), которые атомарно заменяются через `iptables-restore`. pve-firewall и ваши собственные правила не затрагиваются.
- **Выбор гостевой системы.** Показывает локальные ВМ и CT с их IP (из QEMU guest agent, ARP-таблицы хоста, cloud-init или конфигурации LXC; см. [IP гостевых систем](#ip-гостевых-систем)).
- **Сеть хоста как на ладони.** На вкладках «Порты» и «Домены» видны интерфейсы и IP хоста (публичные, WAN, мосты гостевых систем) с подсказками, куда должны указывать DNS и роутеры.
- Поддерживаются TCP, UDP или оба сразу, диапазоны портов, список разрешённых IP/CIDR источников, входящий интерфейс, опциональный masquerade, а также счётчики обращений для каждого правила.
- **Группы.** Правила проброса портов и домены можно объединять в группы (например, *web*, *games*). Каждая группа — это сворачиваемый раздел с собственными кнопками **+ Добавить**, **Переименовать** и **Разгруппировать**. Всё, что не входит в группу, включая сохранённое старыми версиями, остаётся в группе **default**. Пока все элементы в default, таблицы выглядят как раньше. Группы влияют только на отображение; на iptables и nginx они не влияют.
- **Закрепление.** Кнопка 🔓 закрепляет правило или домен (🔒). Закреплённый элемент нельзя изменить, выключить, удалить или перенести в другую группу, пока вы его не открепите. Это проверяется и на сервере (HTTP 423), а не только в интерфейсе. Проверка и выпуск сертификата при этом работают.
- **Языки.** Веб-интерфейс доступен на английском, русском и узбекском (латиница). Язык берётся из браузера, а переключить его можно в **Настройки → Язык** или на странице входа. Сообщения сервера, проверки и ошибки тоже переводятся; CLI и журнал остаются на английском.
- **Защита от ошибок.** Проброс портов 22, 8006, 3128, 111, 5405-5412 и собственного порта запрещён. Пробрасывается только трафик, **адресованный самому хосту** (`-m addrtype --dst-type LOCAL`), поэтому исходящий трафик гостевых систем никогда не перехватывается.
- Watchdog заново подключает цепочки, если кто-то очистил iptables, а при загрузке правила восстанавливаются.

## Установка (на хосте Proxmox, от root)

Одна команда скачивает, устанавливает и запускает сервис:

```bash
curl -fsSL https://raw.githubusercontent.com/farruxx/pve-gateway/master/install.sh | sh
```

Затем откройте `https://<proxmox-ip>:8099` и войдите как `root@pam`.

Для вкладки **Домены** (обратный прокси по имени хоста) установите nginx и certbot. Это единственные опциональные зависимости, обе из Debian:

```bash
curl -fsSL https://raw.githubusercontent.com/farruxx/pve-gateway/master/install.sh | sh -s -- --with-nginx
```

Для **wildcard-сертификатов** добавьте ещё плагин certbot для вашего DNS-провайдера, например Cloudflare (см. [wildcard.md](wildcard.md)):

```bash
curl -fsSL https://raw.githubusercontent.com/farruxx/pve-gateway/master/install.sh | sh -s -- --with-dns cloudflare
```

**Обновление:** в **Настройки → Обновления** нажмите **Обновить до vX.Y.Z** или включите *Устанавливать новые версии автоматически*. pve-gateway раз в день проверяет GitHub и, когда выходит новая версия, показывает значок в шапке вместе со списком изменений (из [CHANGELOG.md](CHANGELOG.md)). Из консоли выполните `pve-gateway update` или повторите команду установки. В любом случае ваши правила, домены и сертификаты сохраняются.

- **Нет подписки Proxmox?** Это обычная ситуация, и она обрабатывается автоматически. Без подписки *enterprise*-репозитории Proxmox отвечают `401 Unauthorized`. Увидев это, установщик переключает apt на бесплатные **no-subscription**-репозитории:
  - enterprise-записи (pve и ceph) отключаются, а не удаляются;
  - добавляются соответствующие no-subscription-записи для того же релиза Debian;
  - резервная копия старых файлов сохраняется в `/var/lib/pve-gateway/apt-backup/`.

  Работает на PVE 8 (`.list`) и PVE 9 (`.sources`). Это безопасно при работающих ВМ: ничего не обновляется и не перезапускается. Хосты с действующей подпиской не затрагиваются. Чтобы пропустить переключение, используйте `--keep-repos`, а чтобы выполнить только его:

  ```bash
  curl -fsSL https://raw.githubusercontent.com/farruxx/pve-gateway/master/install.sh | sh -s -- fix-repos
  ```
- **Хотите сначала прочитать код?** Клонируйте репозиторий и запустите скрипт из него; тогда он использует локальные файлы, а не скачивает их:

  ```bash
  git clone https://github.com/farruxx/pve-gateway && cd pve-gateway && sh install.sh --with-nginx
  ```

### IP гостевых систем

Выбор гостевой системы берёт IP ВМ из **QEMU guest agent**, если он запущен. Без агента используется **ARP-таблица** хоста (по MAC-адресу ВМ), затем **SDN IPAM** (гостевые системы в VNet с DHCP, см. [Сеть](#сеть-dhcp-ipam-и-dns-proxmox-sdn)), а затем `ipconfig` из **cloud-init**.

ВМ, у которой шлюзом служит другой роутер (например, ВМ с файрволом), никогда не обращается к самому хосту, поэтому её нет в ARP-таблице. Для таких ВМ выбор гостевой системы ненадолго опрашивает адреса на приватных мостах хоста (не чаще раза в 5 минут и никогда — на uplink), чтобы они ответили на ARP и появились в списке. Для контейнеров IP берётся из LXC или конфигурации контейнера. Если у ВМ всё ещё *IP неизвестен*:
- установите агент в ВМ (`apt install qemu-guest-agent`),
- включите **Options → QEMU Guest Agent** для ВМ в Proxmox и перезапустите ВМ.

IP всегда можно ввести вручную.

## Домены (обратный прокси nginx)

Вкладка **Домены** сопоставляет имена хостов с гостевыми системами: `cloud.example.com` → `10.10.10.13:80`, `git.example.com` → `https://10.10.10.10:443` и так далее. nginx на хосте слушает порты 80 и 443 и проксирует каждый запрос по заголовку `Host`, так что много гостевых систем могут использовать один публичный IP и одни и те же порты.

- Всё записывается в один генерируемый файл, `/etc/nginx/conf.d/pve-gateway.conf`. Другие сайты nginx не затрагиваются. Каждое изменение проверяется через `nginx -t` перед перезагрузкой; если проверка не прошла, восстанавливается предыдущий файл, а ошибка показывается в интерфейсе.
- **Let's Encrypt** (опционально, для каждого домена) использует `certbot certonly --webroot`. Сертификат запрашивается в фоне сразу после сохранения, а продлевает его собственный systemd-таймер certbot, перезагружая nginx через deploy-хук. *Cert* запрашивает сертификат заново по требованию, а *Test* проверяет DNS, nginx, бэкенд (upstream), сертификат и реальный запрос через nginx.
- **Настройки домена:**
  - псевдонимы (дополнительные имена хостов), которые обслуживаются как тот же сайт или **перенаправляются с кодом 301** на основной домен;
  - HTTPS-бэкенд (самоподписанные сертификаты принимаются);
  - перенаправление HTTP на HTTPS и опциональный **HSTS**;
  - **заголовки безопасности** (nosniff, встраивание только с того же источника, referrer policy);
  - максимальный размер загрузки и разрешённые IP/CIDR источников;
  - **За Cloudflare**: для доменов за «оранжевым облаком» nginx доверяет диапазонам адресов Cloudflare, поэтому журналы, гостевая система и *Разрешённые источники* видят реальный IP посетителя.

  WebSocket работает всегда.
- **Проверка** смотрит DNS (записи A, AAAA и проксируемые через Cloudflare), nginx и бэкенд. Она также проверяет сертификат, который nginx **фактически отдаёт**: он должен покрывать все имена, не быть близким к истечению и совпадать для IPv4 и IPv6. Псевдонимы с перенаправлением должны отвечать кодом 301.
- **Требования:** A-запись DNS каждого домена должна указывать на публичный IP хоста. Если хост находится за роутером, роутер должен пробрасывать на него TCP 80 и 443.
- Пока включён хотя бы один домен, правила проброса портов не могут занимать TCP 80 и 443, потому что эти порты принадлежат nginx. Обратное ограничение тоже действует.

### Wildcard-сертификаты (`*.example.com`)

> Пошаговая настройка (записи DNS, API-токены, устранение неполадок): см. [wildcard.md](wildcard.md).

Один сертификат покрывает `example.com` и все поддомены `*.example.com`. Let's Encrypt выдаёт wildcard-сертификаты только через проверку **DNS-01**, поэтому certbot создаёт TXT-запись через API вашего DNS-провайдера. Порт 80 при этом может быть закрыт.

1. Установите плагин certbot для вашего провайдера (все они — пакеты Debian):

   ```bash
   apt install python3-certbot-dns-cloudflare
   ```

2. Откройте **Домены → Wildcard-сертификаты → + Добавить wildcard** и укажите зону (`example.com`), провайдера и API-токен. Сертификат выпускается сразу (~30 с).
3. Для каждого домена выберите **HTTPS: Wildcard-сертификат (DNS)**. Подходящий сертификат подбирается автоматически, поэтому новый поддомен сразу работает по HTTPS.

| Провайдер | Пакет | Учётные данные |
|---|---|---|
| Cloudflare | `python3-certbot-dns-cloudflare` | API-токен с правами *Zone / DNS / Edit* |
| DigitalOcean | `python3-certbot-dns-digitalocean` | API-токен |
| Linode / Akamai | `python3-certbot-dns-linode` | API-токен |
| DNSimple | `python3-certbot-dns-dnsimple` | API-токен |
| OVH | `python3-certbot-dns-ovh` | endpoint + application key/secret + consumer key |
| RFC 2136 (BIND, PowerDNS, Knot) | `python3-certbot-dns-rfc2136` | сервер, имя/секрет/алгоритм ключа TSIG |

- **Покрытие:** wildcard-сертификат покрывает только один уровень. `*.example.com` подходит для `a.example.com`, но не для `a.b.example.com`; для этого нужно добавить wildcard для `b.example.com`.
- **Учётные данные** записываются в `/etc/pve-gateway/dns/<id>.ini` (права 0600, каталог 0700). Они никогда не возвращаются через API и не попадают в отчёт отладки. Если при редактировании оставить поле пустым, сохранённое значение не изменится.
- **Продление:** таймер certbot продлевает wildcard-сертификаты через тот же DNS-плагин. Wildcard-сертификат, который ещё используют домены, нельзя удалить или выключить.

## Типичная настройка

Гостевые системы находятся на приватном мосту (например, `vmbr1`, `10.10.10.0/24`), а хост выполняет для них NAT. Добавьте правило вроде:

| Порт хоста | Назначение | Смысл |
|---|---|---|
| `8080` | `10.10.10.10:80` | `http://<host-ip>:8080` ведёт на веб-сервер ВМ 100 |
| `27015-27020` TCP+UDP | `10.10.10.12` | диапазон портов, те же порты на гостевой системе |

**Masquerade** нужен, только если шлюз по умолчанию у гостевой системы — *не* хост Proxmox, или если другим гостевым системам нужно обращаться к сервису через публичный IP хоста (hairpin NAT). Учтите, что с включённым masquerade гостевая система видит IP хоста, а не реальный IP клиента.

## CLI

```
pve-gateway serve           # web UI (what systemd runs)
pve-gateway status          # rules, hit counters, hook status
pve-gateway test [NAME...]  # reachability test (rule id/name/host port or domain; default: all enabled)
pve-gateway ui-allow IP...  # web UI only from these IPs/networks ("any" = everyone, no args = show)
pve-gateway ui-host NAME..  # extra hostnames the web UI may be opened by ("none" = clear)
pve-gateway --version       # installed version
pve-gateway update [check]  # install the latest version from GitHub ("check" = only check)
pve-gateway monitors        # run every health check once
pve-gateway scan IP [PORTS] # TCP port scan from this host (common | 22,80,8000-8100)
pve-gateway domains         # list domains, wildcard certificates and expiry
pve-gateway cert NAME       # request / renew now: a domain, or '*.example.com' for a wildcard
pve-gateway backup [FILE]   # backup (config + secrets; --no-secrets, --certs) to FILE or /etc/pve-gateway/backups
pve-gateway backup list     # list local backups
pve-gateway restore NAME|FILE all|PART...   # parts: rules domains monitoring firewall fail2ban vpn access updates
pve-gateway debug           # full diagnostic report, paste it when asking for help
pve-gateway show            # print the generated iptables-restore payload
pve-gateway apply           # re-apply saved rules
pve-gateway flush           # remove all forwarding rules/chains (config kept)
pve-gateway passwd          # use a local user/password instead of Proxmox login
pve-gateway -v ...          # verbose: log every iptables command and HTTP request
pve-gateway --dry-run ...   # log iptables commands instead of running them (for testing)
```

## Отладка

**Вкладка «Отладка»** в веб-интерфейсе:
- **Проверки:** root, iptables, `ip_forward`, существует ли каждый хук и где он стоит в своей цепочке, совпадают ли правила в ядре с конфигурацией, политика FORWARD, статус pve-firewall и сервисы хоста, слушающие проброшенный порт.
- **Сырой вывод:** сгенерированный набор правил, загруженные правила `PVEGW_*` со счётчиками пакетов и байтов, полные цепочки PREROUTING/POSTROUTING/FORWARD, отслеживаемые соединения с гостевыми системами, интерфейсы, маршруты, слушающие сокеты и конфигурация (хэш пароля скрыт).
- **Журнал сервиса:** последние 500 строк в памяти, плюс переключатель *Подробное журналирование*, который действует сразу, без перезапуска.
- **Копировать отчёт / Скачать отчёт:** тот же текст, что и `pve-gateway debug`.

Кнопка **Проверить** у каждого правила (или `pve-gateway test`) запускается с хоста и проверяет:
- правило загружено
- `ip_forward` включён
- маршрут до гостевой системы (и идёт ли он через шлюз)
- ping до гостевой системы
- TCP-подключение к порту гостевой системы, которое отличает отказ (ничего не слушает) от таймаута (гостевая система выключена или закрыта файрволом)
- счётчик обращений правила

Проверки охватывают только сторону гостевой системы. Если при проверке снаружи счётчик остаётся на 0, трафик не доходит до хоста — проверьте роутер, провайдера или облачный файрвол.

Журналы сервиса: `journalctl -u pve-gateway -f`. Чтобы подробное журналирование было включено постоянно, измените `ExecStart` в юните на `... pve-gateway -v serve`.

## Локальная разработка (macOS)

`--mock` запускает всё на симулированном хосте Proxmox. Не нужны ни root, ни iptables, ни Proxmox. Mock имитирует `iptables`, `iptables-restore`/`-save`, `ip`, `ping`, `ss`, `conntrack`, `pve-firewall`, `pvesh` (включая SDN), `qm`, `pct`, `lxc-info`, `dnsmasq` и другое. Код mock находится в [`dev/mock.py`](dev/mock.py) и никогда не устанавливается на хост.

```bash
./dev.sh
```

Откройте http://127.0.0.1:8099 и войдите как **admin / admin**.

Любую команду CLI можно запустить на том же симулированном хосте. Веб-интерфейс и CLI используют общее состояние через `.dev/mock-state.json`:

```bash
./dev.sh status
```
```bash
./dev.sh test
```
```bash
./dev.sh debug
```

Чтобы намеренно сломать хост, запустите сценарий. Они также доступны кнопками на вкладке «Отладка»:

```bash
./dev.sh mock unhook
```

| Сценарий | Что делает |
|---|---|
| `unhook` | удаляет наши правила перехода. Проверки не проходят, а watchdog исправляет это в течение 10 с |
| `ip-forward-off` | устанавливает `net.ipv4.ip_forward = 0` |
| `forward-drop` | устанавливает политику FORWARD в DROP |
| `pvefw-first` | ставит переход pve-firewall выше нашего (предупреждение) |
| `foreign-dnat` | ставит чужое правило DNAT выше нашего хука (предупреждение) |
| `traffic` | отправляет пачку обращений в счётчики |
| `nginx-stopped` | останавливает nginx, так что проверки доменов не проходят |
| `nginx-test-fails` | делает следующий `nginx -t` неудачным, демонстрируя откат |
| `cert-expiring` | все сертификаты истекают через 5 дней |
| `no-dnsmasq` | dnsmasq отсутствует, поэтому SDN DHCP не работает (кнопка установки на вкладке «Сеть») |
| `no-sdn` | старый Proxmox VE (7.4) без API SDN |
| `sdn-pending` | изменение SDN, сделанное в другом месте и ещё не применённое |
| `reset` | очищает симулированный iptables |

Симулированные гостевые системы: 100 web, 101 db, 102 game (остановлена), 103 nextcloud, 104 win11 (без guest agent, не отвечает на ping), 105 office-gw (за шлюзом) и 108 builder (в SDN VNet `labnet`, находится через IPAM). Демонстрационный SDN содержит зону `lab` (DHCP, плагин PowerDNS), VNet `labnet` и подсеть `10.20.30.0/24`. Демонстрационные правила показывают все возможные результаты проверки. Демонстрационные домены: `cloud.example.com` (HTTPS работает), `app.example.com` (только HTTP, с псевдонимом) и `broken.invalid` (нет DNS, и бэкенд ничего не слушает). Демонстрационный wildcard-сертификат — `*.example.com` (Cloudflare), его использует `status.example.com`. Mock-certbot завершается с ошибкой для имён, оканчивающихся на `.invalid`, а для всех остальных успешно выполняется через 2 с. Для wildcard-сертификатов API-токен `bad` получает ошибку Cloudflare «invalid credentials», а установленными считаются только плагины Cloudflare, DigitalOcean и RFC 2136, поэтому для OVH показывается сообщение «плагин отсутствует». Сгенерированные файлы nginx попадают в `.dev/mock-fs/`. Удалите `.dev/`, чтобы начать заново.

`--dry-run` — это другое. Он предназначен для **реального** хоста: команды только для чтения выполняются по-настоящему, а изменения лишь записываются в журнал.

## Мониторинг

Вкладка **Мониторинг** следит за вашими гостевыми системами и доменами:

- **Проверки:** HTTP(S) (ожидаемый статус, срок действия сертификата), TCP-порт и ping каждые N секунд. Для каждой проверки показываются статус (работает / сбои / недоступен), время ответа, аптайм и последние 60 результатов. **Добавить проверки для моих доменов и портов** создаёт по одной проверке на каждый домен и правило проброса портов.
- **Оповещения:** отправляются, когда проверка недоступна N раз подряд, когда она снова работает и когда сертификат истекает в течение N дней. Каналы:
  - **e-mail** через почтовую систему хоста (в Proxmox есть postfix);
  - **вебхук** (Slack, Discord или любой URL; JSON с `text`/`content`);
  - **Telegram** (токен бота + chat id).

  **Отправить тестовое оповещение** проверяет настройку. Токены хранятся только на хосте и больше никогда не показываются.
- **Сканер портов:** TCP connect-сканирование с хоста (около 90 распространённых портов или диапазоны до 5000) с названиями сервисов и уровнями риска. Он показывает, что доступно самому хосту; из интернета картина может отличаться. Чтобы исключить злоупотребления, сканировать можно только этот хост, приватные сети и известные гостевые системы.

CLI: `pve-gateway monitors` один раз запускает все проверки; `pve-gateway scan 10.10.10.11 1-1024` сканирует из консоли.

## WireGuard VPN

Вкладка **VPN** настраивает WireGuard на хосте:
- **Туннели:** новый туннель заполняется разумными значениями по умолчанию: свободная подсеть `10.99.x.0/24`, UDP 51820, публичный адрес этого хоста как endpoint и мосты гостевых систем как сети, доступные клиентам. Ключи генерируются на хосте, а туннель запускается сразу и при загрузке (`wg-quick@wg0`).
- **Устройства** (телефон, ноутбук): для них генерируются ключи, и вы получаете **конфигурацию клиента** для импорта в приложение WireGuard (просмотр, копирование или скачивание).
- **Площадки** (другой роутер или офис): вставьте их публичный ключ, а также сети за ними, endpoint и keepalive.
- **Сведения об узлах:** опциональные pre-shared ключи и статус каждого узла в реальном времени: в сети, последний handshake, endpoint и трафик.

Изменения узлов применяются через `wg syncconf`, поэтому подключённые клиенты не отключаются. Произвольных строк `PostUp` нет. NAT для VPN-клиентов (*NAT в сети гостевых систем*) и проброс реализованы правилами iptables pve-gateway, а порт WireGuard автоматически открывается в файрволе pve-gateway. Приватные ключи хранятся в `/etc/pve-gateway/wireguard/` и `/etc/wireguard/` (права 0600); они никогда не попадают в `config.json`, API или отчёт отладки.

## Сеть: DHCP, IPAM и DNS (Proxmox SDN)

Вкладка **Сеть** управляет [Proxmox SDN](https://pve.proxmox.com/pve-docs/chapter-pvesdn.html) через API Proxmox, поэтому всё также видно в разделе *Datacenter → SDN* интерфейса Proxmox. pve-gateway не хранит собственную копию. Требуется Proxmox VE 8.1 или новее.

- **Зоны:** новые зоны создаются как *simple*-зоны: изолированные мосты на этом хосте, без настройки VLAN. Каждая зона может раздавать адреса по **DHCP** (Proxmox запускает по одному dnsmasq на зону; кнопка **Установить dnsmasq** устанавливает его и отключает экземпляр по умолчанию). Учёт адресов ведёт встроенный IPAM Proxmox. Зоны VLAN, VXLAN и EVPN, созданные в интерфейсе Proxmox, отображаются, но не редактируются.
- **VNet** становятся мостами с именем VNet. Чтобы подключить гостевую систему, укажите VNet в качестве моста её сетевого устройства (*Hardware → Network Device → Bridge*). Вкладка показывает, какие гостевые системы используют какой VNet, и не даёт удалить VNet, в котором ещё есть гостевые системы.
- **Подсети:** шлюз (адрес этого хоста в VNet), **SNAT** (гостевые системы выходят в интернет через хост), диапазоны DHCP и DNS-сервер, выдаваемый клиентам DHCP. Подсети, пересекающиеся с сетями хоста, другими подсетями или туннелями WireGuard, отклоняются.
- **IPAM:** все адреса, выданные Proxmox (с гостевой системой и именем хоста) или зарезервированные. **+ Резервирование** закрепляет IP за MAC-адресом; вместо ввода MAC можно выбрать сетевую карту гостевой системы.
- **DNS:** выберите DNS-плагин Proxmox SDN (PowerDNS) и домен для каждой зоны, и Proxmox будет регистрировать имена гостевых систем. Сам плагин добавьте в интерфейсе Proxmox (*Datacenter → SDN → Options*), чтобы его API-ключ оставался в Proxmox; pve-gateway никогда его не читает и не показывает.

Изменения ожидают в Proxmox, пока вы не нажмёте **Применить изменения SDN**, как и в интерфейсе Proxmox. Применение перезагружает сети SDN. Когда файрвол pve-gateway включён, DHCP (UDP 67) разрешён только в VNet с DHCP и никогда — на uplink. Гостевые системы, получившие адрес от SDN DHCP, находятся через IPAM при выборе гостевой системы, так что на вкладке «Порты» на них можно пробрасывать порты. Вкладка «Отладка» проверяет dnsmasq, `source /etc/network/interfaces.d/*`, ожидающие изменения, мосты VNet и DHCP-серверы каждой зоны.

## Файрвол

**Безопасность → Файрвол** защищает сам хост (входящий трафик). Вы выбираете бэкенд:
- **pve-gateway**: собственная цепочка `PVEGW_IN` для iptables и ip6tables, подключённая первой в `INPUT`.
- **Файрвол Proxmox**: pve-gateway создаёт свои правила (с комментарием `pvegw: …`) в начале файрвола узла через API Proxmox, поэтому они видны и в интерфейсе Proxmox. Ваши собственные правила Proxmox не затрагиваются и показываются ниже.

Правила — это упорядоченные записи **allow / drop / reject**:
- протокол TCP, UDP, ICMP или любой;
- списки и диапазоны портов;
- опциональная сеть-источник;
- комментарий.

Политика по умолчанию — *разрешить всё остальное* или *отбросить всё остальное*. Шаблоны добавляют типовые наборы (web, почта, DNS, WireGuard, SSH, Proxmox, базы данных только из приватных сетей). **Открытые сейчас рискованные порты → только LAN** использует проверку доступности, чтобы скрыть из интернета сервисы вроде rpcbind или баз данных.

**Заблокировать себе доступ невозможно:**
- **Всегда открыты:** SSH, интерфейс Proxmox (8006), собственный порт pve-gateway (с его разрешённых источников), 80/443, пока у вас есть домены, порты кластера на кластерах и установленные соединения. Правило drop для *всех* на 22/8006/порт интерфейса отклоняется.
- **Каждое изменение сначала временное:** у вас есть **60 секунд, чтобы нажать «Оставить»**. Если страница больше не может связаться с сервером, предыдущий файрвол возвращается сам. Неподтверждённые изменения никогда не сохраняются, поэтому перезапуск тоже возвращает старые правила.

## Fail2ban

Вкладка **Безопасность** показывает jail'ы fail2ban с числом неудачных попыток и блокировок. Все заблокированные IP собраны в один список с поиском (IP, jail и сколько блокировок приходится на ту же сеть) с кнопкой **Копировать список**. Можно **разбанить** один IP или все сразу и **забанить** IP вручную (но никогда не ваш собственный IP или localhost). **Установить fail2ban** настраивает его, если он отсутствует.

Включите *Управлять fail2ban через pve-gateway*, чтобы настраивать его из интерфейса: время блокировки, окно поиска, число неудачных попыток до блокировки, список **никогда не банить** и следующие jail'ы:
- **sshd**: входы по SSH.
- **proxmox**: неудачные входы в веб-интерфейс Proxmox (порт 8006), читаются из `pvedaemon` в журнале.
- **pve-gateway**: неудачные входы в этот интерфейс.
- **nginx-botsearch**: боты, ищущие несуществующие страницы. Запросы к `/.well-known/acme-challenge/` никогда не учитываются, поэтому серверы проверки Let's Encrypt не могут быть заблокированы после неудачной попытки получить сертификат.
- **recidive**: повторная блокировка в течение суток → блокировка на неделю.

pve-gateway записывает `/etc/fail2ban/jail.d/pve-gateway.local` (читается последним, поэтому переопределяет `jail.local`) и собственные фильтры `pvegw-*`. Каждое изменение проверяется через `fail2ban-client -t`, а при ошибке восстанавливаются предыдущие файлы. Если снять галочку, файл удаляется.

## Защита веб-интерфейса

Интерфейс работает от root, может менять файрвол и nginx хоста и входит под `root@pam`. Не оставляйте его открытым в интернет:

- **Ограничьте, кто может подключаться:** откройте **Настройки → Доступ к веб-интерфейсу** и перечислите IP/сети, которым разрешено открывать страницу, например IP вашего офиса или диапазон VPN. Всем остальным отказывается ещё до того, как они увидят форму входа.
  - Подключения с самого хоста (`localhost`, например через ssh-туннель) работают всегда.
  - Интерфейс не примет список, который заблокирует IP, с которого вы его сохраняете.
  - Из ssh-сессии: `pve-gateway ui-allow 203.0.113.7 10.20.0.0/24`, или `pve-gateway ui-allow any`, чтобы отменить.
- **Защита входа:**
  - После 5 неудачных входов IP блокируется на 15 минут.
  - С одного IP одновременно проверяется только один вход, поэтому параллельный подбор не помогает.
  - Учётные записи Proxmox с **двухфакторной аутентификацией (TOTP)** поддерживаются: при входе запрашивается код.
- **Сессии** привязаны к IP и браузеру, из которых они созданы, поэтому скопированный cookie в другом месте бесполезен. Браузеры не разделяют cookie по портам, так что иначе его мог бы увидеть гостевой сервис, открытый на том же IP хоста.
- **Разрешённые пользователи Proxmox:** по умолчанию только `root@pam`. Других пользователей можно добавить в **Настройках** (формат `name@realm`).
- **Проверка доступности:** вкладка «Отладка» предупреждает о рискованных сервисах (rpcbind, базы данных, Redis, Docker API, VNC, …), слушающих все интерфейсы, а также о включённых enterprise-репозиториях без подписки.
- **Проверка имени хоста:** интерфейс отвечает только на IP-адреса, собственные имена этого хоста и добавленные вами имена хостов (в Настройках или `pve-gateway ui-host pve.example.com`). Это блокирует атаки DNS rebinding.

## Конфигурация: `/etc/pve-gateway/config.json`

Здесь же хранятся правила. После ручного редактирования перезапустите сервис.

```json
{
  "listen": "0.0.0.0",
  "port": 8099,
  "allowed_users": ["root@pam"],
  "protected_ports": ["22", "8006", "3128", "111", "5405-5412"],
  "forward_accept": true
}
```

- `allowed_users`: пользователи Proxmox, которым разрешён вход. Учётные записи с включённой TFA не поддерживаются; используйте вместо этого `passwd`.
- `forward_accept`: добавляет узкие правила `ACCEPT` в `FORWARD` для проброшенных потоков. Они вставляются перед `PVEFW-FORWARD`, поэтому если для гостевой системы включён файрвол Proxmox, проброшенный порт обходит её файрвол. Чтобы ограничить доступ, используйте поле *Разрешённый источник* в правиле.
- `listen`: укажите IP в LAN (например, `192.168.1.10`), чтобы интерфейс не был доступен на публичном интерфейсе.
- `group` (у каждого правила и домена): группа, в которой он отображается; если значение отсутствует или некорректно, используется `default`.
- `locked` (у каждого правила и домена): `true` защищает его от изменений через интерфейс и API.

## Доверенный HTTPS (Let's Encrypt)

По умолчанию Proxmox использует самоподписанный сертификат, поэтому браузеры показывают предупреждение и на `:8006`, и на `:8099`. Выдайте Proxmox настоящий сертификат, и pve-gateway тоже будет его использовать. Продлённые сертификаты подхватываются в течение 5 минут, без перезапуска.

Вот пример для домена на DNS Cloudflare. Используется проверка DNS-01, поэтому порт 80 открывать не нужно. Создайте API-токен Cloudflare с правами *Zone → DNS → Edit* для зоны, затем выполните на хосте:

```bash
pvenode acme account register default you@example.com --directory https://acme-v02.api.letsencrypt.org/directory
printf 'CF_Token=<token>\n' > /root/cf.env
pvenode acme plugin add dns cloudflare --api cf --data /root/cf.env && rm /root/cf.env
pvenode config set --acmedomain0 pve.example.com,plugin=cloudflare
pvenode acme cert order
```

## Резервное копирование и восстановление

**Настройки → Резервные копии** сохраняют всё, что знает pve-gateway, в один файл `.tar.gz`:
- конфигурацию: правила, домены, wildcard-сертификаты, проверки и оповещения, файрвол, fail2ban, VPN и настройки;
- по желанию секреты, хранящиеся отдельно от неё: учётные данные DNS API, ключи WireGuard, токены оповещений и хеш пароля. **Файл с секретами нужно хранить в тайне.**
- по желанию сертификаты Let's Encrypt для доменов.

Копии хранятся на хосте в `/etc/pve-gateway/backups` (папка 0700, файлы 0600):
- ручные копии;
- **ежедневная автоматическая копия** (последние 7);
- **страховочная копия перед каждым восстановлением**, так что восстановление всегда можно отменить.

Скачайте копию, чтобы хранить её в другом месте. Так же pve-gateway переносится на новый хост: установите его там, загрузите файл и восстановите.

**Восстановление** показывает содержимое копии и позволяет выбрать части: правила портов, домены и wildcard-сертификаты, проверки и оповещения, файрвол, fail2ban, VPN, доступ к веб-интерфейсу, настройки обновлений. Всё остальное остаётся как есть.
- **Никогда не восстанавливаются:** настройки, зависящие от хоста (порт, TLS-сертификат интерфейса, пути к файлам).
- **Файрвол:** восстановленный включённый файрвол нужно подтвердить в течение 60 с, как любое изменение файрвола.
- **Защита от потери доступа:** настройки доступа к веб-интерфейсу, из-за которых вы потеряете доступ, отклоняются.
- **При ошибке:** если применение не удалось (например, `nginx -t`), возвращаются прежняя конфигурация и файлы секретов.
- **Сертификаты:** восстанавливаются, только если на хосте их нет, поэтому существующие никогда не перезаписываются.
- **Копии без секретов:** учётные данные DNS, ключи WireGuard и пароль, уже имеющиеся на хосте, сохраняются.

Загружаемые файлы строго проверяются: только известные имена файлов, никаких путей за пределами копии, символические ссылки только между папками `live/` и `archive/` certbot.
